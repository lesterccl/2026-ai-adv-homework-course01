# 首次盤點缺口清單

## 目標

把 2026-09-02 對整個 repo 做過一輪盤點後確認的缺口記錄下來，作為後續開卡的來源。

**這份不是執行卡**——它是待辦池。要動其中任何一項，複製 [TEMPLATE.md](./TEMPLATE.md) 另開一張卡，把該項的內容搬過去展開。

## 背景

專案初始狀態（commit `004e507`）的功能已大致完整：認證、商品、購物車雙軌、訂單、模擬付款、後台商品 CRUD、後台訂單檢視都能運作，測試 6 檔 32 案例。

盤點方式是逐檔讀 `src/`、`tests/`、`public/js/`、`views/`，下列每一項都有 `路徑:行號` 佐證，不是推測。詳細說明見 [FEATURES.md §7](../FEATURES.md) 與 [TESTING.md §8](../TESTING.md)。

## 待辦項目

### B-1 後台無法修改訂單狀態

- **現況**：`src/routes/adminOrderRoutes.js` 只有 `router.get('/')`（:83）與 `router.get('/:id')`（:192），沒有任何寫入端點。前端 `public/js/pages/admin-orders.js` 也只有篩選與檢視。
- **影響**：管理員無法調整訂單狀態，訂單一旦進入 `paid` / `failed` 就凍結。這是後台管理最基本的缺口。
- **建議做法**：新增 `PATCH /api/admin/orders/:id`，body `{ status }`，值限於 DB CHECK 允許的 `pending` / `paid` / `failed`。若要支援出貨/取消等狀態，得先改 `src/database.js` 的 CHECK 約束（**需刪 DB 重建**，見 ARCHITECTURE.md §5.3），屬較大改動。
- **連帶**：`admin-orders.js` 加操作 UI、補 `@openapi` 區塊、`adminOrders.test.js` 補測試。
- **規模**：中

### B-2 登入不合併訪客購物車

- **現況**：`src/routes/authRoutes.js` 全檔零 `session_id` / `cart_items` 引用；`sessionMiddleware.js` 只做 header → `req.sessionId`，沒有合併邏輯。
- **影響**：訪客加購 → 登入 → 購物車變空。使用者體驗上的明顯斷點。
- **建議做法**：登入與註冊成功後，若請求帶了 `X-Session-Id`，把該 session 的 `cart_items` 轉移到 `user_id`。要處理同商品在兩邊都有的合併（累加數量並刪除重複列），且應包在 `db.transaction()` 內。
- **注意**：`POST /api/auth/register` 也是「註冊即登入」，同樣要處理。
- **規模**：中

### B-3 付款是純本地模擬，ECPay 未串接

- **現況**：`.env.example:12-16` 宣告了 `ECPAY_MERCHANT_ID` / `ECPAY_HASH_KEY` / `ECPAY_HASH_IV` / `ECPAY_ENV`，但 `grep -ri ecpay src/ public/ views/ tests/` **零匹配**。實際流程是前端呼叫 `PATCH /api/orders/:id/pay`（`public/js/pages/order-detail.js:31`），後端直接改 status。
- **影響**：沒有真實金流。以作業/demo 而言可接受，但環境變數的存在會讓人誤以為已經串了。
- **選項**：
  - (a) 真的串綠界測試環境：需要 CheckMacValue 計算、付款頁跳轉、`ReturnURL` 回調端點（回調不帶 JWT，得另設驗證方式）。**規模大**。
  - (b) 維持模擬，把 `ECPAY_*` 從 `.env.example` 移除，消除誤導。**規模小**。
- **建議**：先做 (b) 止血；(a) 要不要做是商業判斷，交 user 決定。

### B-4 `GET /api/auth/profile` 前端未使用

- **現況**：端點存在（`authRoutes.js:263`）且有測試，但 `grep -rn "auth/profile" public/ views/` 零匹配。header 的使用者名稱來自 localStorage 的 `Auth.getUser()`，不是這支 API。
- **影響**：小。但 localStorage 的使用者資料不會隨伺服器端變動更新（例如 admin 改了某人的名字）。
- **建議做法**：二選一——做一個「會員中心」頁面來用它，或在 `header-init.js` 改用它取得最新資料。也可以評估是否直接移除該端點。
- **規模**：小

### B-5 測試覆蓋缺口

- **現況**：完整清單見 [TESTING.md §8](../TESTING.md)（10 項）。
- **最該優先的兩項**：
  1. `PATCH /api/orders/:id/pay` **整支端點零測試**——這是唯一會改變訂單狀態的端點，卻完全沒有安全網。
  2. `pageRoutes.js` 的 **9 條 SSR 路由零測試**——改動 layout 或 partial 弄壞頁面，只能靠手動開瀏覽器才會發現。用 supertest 打 `GET /` 斷言 200 + HTML 含關鍵字即可，成本很低。
- **規模**：小（可分次補，每次一兩項）

# harness-digest — 制度來源與設計理由

> **這是快照，不是權威版。** 摘錄自本機全域制度 `~/.claude/rules/`（`model-dispatch.md`、`judgment-matrix.md`、`delegation-templates.md`、`reflection-protocol.md`、`harness-diagnosis.md`、`lessons.md`），摘錄日期 **2026-09-02**。
>
> 兩份會漂移。**衝突時以全域版為準**，並回報矛盾點（這本身就是熔斷條件之一）。
> 本檔存在的理由：讓這個 repo 自帶完整制度脈絡，離開本機也讀得懂 `workflow.md` / `delegation.md` / `boundaries.md` 為什麼長這樣。

## 1. 設計哲學

> **凡是靠自覺的防線都會退化，所以關鍵防線全部做成硬門檻（行數上限、次數門檻、hook、權限分層）。你的工作不是發明新防線，是不要拆掉現有的。**

分工是刻意的：

| 層 | 手段 | 擋什麼 |
|---|---|---|
| 物理 | `hooks/`、`settings.json` 的 `deny` | 踩一次就毀掉 session 或不可逆的錯誤 |
| 機械 | `ask` 權限、測試、`npm run openapi` | 需要人確認、或機器可判定對錯的 |
| 散文 | `rules/*.md` | 踩了可恢復、需要判斷力的 |

**散文層是最弱的一層**，本機有明確實證：對 `git add -A`、長路徑連字號、擅自重啟服務這三類失誤，粗體警告被反覆違反（各 2–3 次再犯）。所以它們全部下沉到物理層。

判斷某條規則該放哪一層：**它被違反過幾次？違反的代價可不可逆？** 兩者都高就下沉。

## 2. 檔案分級（Tier）

決定「模型可不可以自己改」：

| Tier | 內容 | 權限 |
|---|---|---|
| **A — 事實層** | `docs/**`、`docs/plans/**`、踩坑紀錄 | **可自行更新**。更新需附驗證證據 |
| **B — 制度層** | `.claude/settings.json`、`.claude/hooks/**`、`.claude/rules/**`、`CLAUDE.md` 的結構與鐵律、`.gitignore`、`.env` | **動之前必須先徵得 user 同意** |

灰色地帶判準：改動會影響**「模型未來的行為方式」**→ Tier B；只影響**「模型知道的事實」**→ Tier A。分不清 → 當 Tier B 問。

在這個 repo，Tier B 已由 `settings.json` 的 `ask`/`deny` 機械化實施——`Edit(.claude/**)` 會跳確認，不是靠你記得。

### 改 Tier B 的程序（user 同意後）

1. `cp <file> <file>.bak`
2. 修改，並在檔案開頭加一行：`> 修訂: YYYY-MM-DD <模型名> — <一句話改了什麼> (user 核准)`
3. Read-back 確認完整

## 3. 這套制度最可能的退化方式

| 退化模式 | 樣貌 | 預防 |
|---|---|---|
| **規則堆積** | 每踩一次坑就加一條，只加不刪 | 硬行數上限 + 同根因 3 則必須合併抽象化 |
| **Hook 侵蝕** | 被擋一次嫌煩 →「暫時」停用 → 永遠停用 | hook 的 stderr 一律附「正確做法」，沒有整組拆掉的理由；hook 屬 Tier B |
| **派工形式化** | 模板照填但驗收條件寫成「做好做完整」；驗收 agent 不實跑就蓋 ACCEPT | 驗收判定必須逐條附命令輸出，無證據 = REJECT。user 抽查時就問一句「把驗證證據貼給我」 |
| **文件漂移** | `docs/` 與代碼實況脫節——**錯的文件比沒文件更毒** | Tier A 更新需附驗證證據；發現錯誤事實 = 當場修 |

## 4. 誠實條款：這套制度救不了的事

以下任務類型**制度也救不了**，遇到時走固定動作：

| 極限 | 例子 | 標準動作 |
|---|---|---|
| 品味 / 美感 | UI 排版、配色、文案語氣 | 做 2–3 候選 + 列客觀 trade-off + 交 user 選。**禁止自行拍板落地** |
| 商業判斷 | 要不要串真金流、要不要引入某套件、這個架構值不值得 | 只報可量化證據，明確標註「經濟/商業合理性判斷需 user」 |
| 跨 session 的長程架構取捨 | 要不要加 service 層、要不要換 ORM | 寫成提案文件（現況/選項/成本/風險），熔斷提問。**禁止直接動工** |
| 資訊查不到 | 未文件化的套件行為 | 先查（原始碼、實測小樣本）；查不到就標 `[UNVERIFIED]`，**禁止編造** |

**自我檢測訊號**：如果驗收條件無法寫成「可用命令或肉眼逐條核對的檢核表」，這件事就屬於上表。

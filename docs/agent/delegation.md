# delegation — 派工與驗收

> 核心命題：主對話的 context 是稀缺資源。raw 檔案內容一旦進了主對話，之後每一輪都在為它付費。

---

## 1. 什麼時候必須派 subagent（量化門檻，不是建議）

| 情境 | 門檻 | 派給 |
|---|---|---|
| 讀檔調查 | 預估要開 **> 3 個檔案** 才能回答 | Explore |
| 關鍵字搜尋 | 第 **2 次** Grep/Glob 還沒找到目標 | Explore |
| 全 repo 掃描 / 慣例調查 | 一律 | Explore |
| 多檔實作 | 改動 **> 2 個檔案** 且 spec 已明確 | general-purpose |
| 機械式批次套用 | 同一 pattern 改 **≥ 3 處** | general-purpose（可用較小模型） |
| 驗收他人實作 | 一律 | fresh-context subagent |

主對話可以自己做：讀 1–3 個已知路徑的檔案、單檔小修改、跑單一命令、寫最終報告。

**反例**：自己 Grep 五輪、開八個檔案找一個函式定義。
**正例**：派 Explore「找出 X 的定義與所有呼叫點，回報 `路徑:行號` 清單」，主對話只收 10 行結論。

## 2. 派工三件套（缺一段就是違規派工）

每個 Agent 呼叫的 prompt 必含：

1. **目標與背景** — 要達成什麼、為什麼、已知線索（相關路徑、已確認的事實、之前試過什麼）。subagent 是全新 context，**你沒寫的它不知道**。
2. **驗收條件** — 可檢查的完成定義。禁止「做好做完整」。
3. **回報格式** — 明確的結構與長度上限。

**強制條款**：回報用 `路徑:行號` 指涉代碼，禁止貼超過 10 行的代碼段，結論先行，總長 ≤ 30 行（研究/審查類可放寬到 60 行）。

### 本專案必加的兩欄

- **【允許路徑】** 白名單。動範圍外的檔案 = 停下回報，不先斬後奏。
- **【Non-goals】** 明列不做的事。預設繼承：
  1. 不改 `.claude/**`（settings、hooks、rules）、`.env`、`.gitignore`
  2. 不 commit / push，除非派工單明示
  3. 不改測試斷言讓自己過
  4. 不重構派工單未提及的模組
  5. 不引入新的 npm 依賴

### 本專案必加的環境提醒

派實作類工作時，派工單要明寫：

> 動手前必讀 `docs/DEVELOPMENT.md`。本 repo 的風格有多處反直覺：API 路由 handler 用箭頭函式但頁面路由用具名 `function`；API 回應欄位保持 DB 的 snake_case，**不要轉 camelCase**（既有測試會全紅）；錯誤一律 `return res.status(N).json({data,error,message})` 早期回傳，不 throw。

## 3. 隔離驗證：實作者不得自我驗收

實作 agent 說「我做完了、測試過了」一律視為**未驗證聲明**。驗收由另一個 fresh-context subagent 執行，三步缺一不可：

1. **Read-back** — 重新從磁碟讀改動後的檔案，不信任轉述。
2. **實跑** — 實際執行測試 / 啟動服務 / 打 request，貼出實際輸出。
3. **逐條核對** — 對照原驗收條件，每條標 PASS（附證據）/ FAIL（附證據）/ 無法驗證（附原因）。

判定只有 **ACCEPT / REJECT**，沒有「大致通過」。任一條 FAIL 或無法驗證 = REJECT。

**為什麼要 fresh context**：實作者的 context 裡充滿「我已經做對了」的自我敘事，會腦補證據。乾淨 context 只看得到磁碟上的事實。

審查員**不准自己動手修**——你是審查員不是實作者。

## 4. 升降級

| 觸發 | 動作 |
|---|---|
| 小模型出現 1 次工具呼叫錯誤或語法錯誤 | 同任務直接升一級，不重試 |
| 同一子任務連錯 2 次（驗收不過算錯） | 帶完整失敗軌跡升級 |
| 最高級在同一子任務兩輪仍失敗 | 熔斷，見 [boundaries.md](./boundaries.md) |

**上限：同一件事最多兩輪升降級循環。第三輪 = 熔斷問 user。**「換個小改法再試一次」不重置計數。

升級時必附失敗軌跡，讓上層不用重踩：

```
目標: <原驗收條件>
嘗試1: <做了什麼> → <確切錯誤訊息>
嘗試2: <做了什麼> → <確切錯誤訊息>
已排除: <確認不是問題的原因>
懷疑: <目前最佳猜測>
涉及檔案: <路徑:行號>
```

**降級省錢**：高階模型解出一個固定模式後（修好第 1 個案例、確立了改法），剩餘同型案例寫成明確 pattern（before/after + 檔案清單）降回小模型批次套用。

## 5. 已知的派工失敗模式

這些是實測過的，**預算進去，不要試圖用措辭預防**：

| 模式 | 現象 | 處置 |
|---|---|---|
| 長命令被自動背景化 | subagent 跑長測試 → 命令轉背景 → agent 回合結束，回報只有「等通知」 | 用 SendMessage 叫回同一個 agent（context 還在）取回輸出。派長跑任務時直接預算這一輪喚醒 |
| 小模型手打長路徑會「自動修正」 | 路徑含不合直覺的連字號/底線混用時被歸一化，報檔案不存在 | 把完整命令寫成 script 讓它只跑 `bash <script>`；或直接派中階模型 |
| 排查衝動壓過禁令 | 派工單寫「不得動 port X」，agent 遇到非預期結果仍去重啟 | 不只寫「禁動」，要把該資源排除在驗證程序之外（明寫「所有 http 驗證僅准 test client」） |
